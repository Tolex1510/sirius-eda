# Учебная практика: платежи, AI-ассистент и веб-интерфейс

Статус: реализован локальный сквозной MVP с demo-оплатой и подключением Ollama.
Настоящий тестовый магазин и оценка модели на WSL остаются отдельными проверками; см. docs/study/RESULTS.md.
Рабочая оценка: 4 недели, два трека D + F. Фактические сроки практики пока не уточнены.
Цель: законченный пользовательский сценарий от выбора еды до оплаты, доставки и вопросов ассистенту.

## 1. Результат для пользователя

Пользователь открывает меню, регистрируется, выбирает блюдо и количество, оформляет заказ,
переходит на тестовую страницу оплаты и видит подтверждённый сервером результат.
В личном кабинете доступны история, состояние доставки и состояние возврата.
Ассистент помогает найти блюда, отвечает по правилам сервиса и объясняет состояние собственных заказов и платежей.

Связь треков для защиты: ассистент использует сведения платёжного модуля для ответов
«Оплачен ли заказ?» и «Что с возвратом?». Доступ к этим данным проверяется на сервере.
Выбор пары D + F нужно согласовать с преподавателем: документ требует логического продолжения первого трека вторым.

## 2. Что есть сейчас и что потребуется изменить

| Сейчас | Изменение |
|---|---|
| FastAPI, модули API → Service → Repository | Новые модули payments и assistant с тем же разделением |
| Деньги списываются с внутреннего баланса при создании | Отдельный сценарий внешней оплаты без списания баланса |
| `/orders/{id}/pay` самостоятельно переводит заказ в paid | Внешний заказ подтверждает только проверенный результат шлюза |
| Один заказ содержит одно блюдо и количество | Сохранить эту модель для первого законченного сценария |
| Цены и суммы в Float | Перевести затрагиваемые денежные поля в Numeric/Decimal, определить округление |
| Отмена компенсируется зачислением внутреннего баланса | Компенсация выбирается по источнику оплаты: баланс или шлюз |
| Трекинг через SSE и gRPC | Использовать существующий трекинг в интерфейсе |
| Генерация PDF/email/SMS имитируется заглушками | Не обещать реальные чеки и отправку писем; отличать их от оплаты |
| Compose запускает PostgreSQL, Redis, RabbitMQ | Добавить приложение, фронтенд, доставку, workers и миграции |
| Есть тесты, миграции и GitHub Actions | Добавить проверки новых сценариев и сборку фронтенда |

Сданные лабораторные остаются точкой отсчёта: адаптируем существующие контракты и тесты осмысленно,
а не сохраняем возможность подтвердить внешнюю оплату старой кнопкой.
Для старых заказов миграция явно указывает источник оплаты internal_balance.
Новые заказы сайта используют gateway. Смешанная оплата не входит в объём.

## 3. Рабочие технические решения

- Фронтенд: React + TypeScript + Vite, маршруты страниц и единый клиент API, каталог `frontend/`.
- Визуальное направление: современная столовая, светлый фон, выразительный акцент, удобное мобильное меню.
- Оплата: ЮKassa, тестовый магазин, переход на размещённую у провайдера страницу оплаты.
- AI: интерфейсы генерации и эмбеддингов; первый кандидат — Ollama, выбор модели после замера на доступной машине.
- RAG: pgvector в существующем PostgreSQL; индексируются меню и отдельная пользовательская справка.
- Данные заказов и платежей: серверные операции чтения, проверяющие пользователя; не общий векторный индекс.
- Запуск: единая точка входа через reverse proxy для фронтенда и `/api`, инфраструктура через Compose.
- Очереди, outbox, повторы и фоновые задачи: использовать существующие RabbitMQ и Celery.

Облачная LLM остаётся альтернативой при недостаточной скорости локальной модели.
Провайдера и модель фиксируем до основной реализации ассистента, после проверки качества русского языка,
эмбеддингов, времени ответа и требований к памяти. Изменение размерности эмбеддингов требует переиндексации.

## 4. Фронтенд: первый законченный объём

| Экран | Функции |
|---|---|
| Меню | Категории, поиск по названию, карточки с ценой и доступностью |
| Вход и регистрация | Email/пароль, понятные ошибки, обновление сессии, выход |
| Оформление | Блюдо, количество, серверная итоговая сумма, создание заказа |
| Оплата и возвращение | Переход к шлюзу, ожидание подтверждения, успех, отказ, неизвестный результат |
| Мои заказы | Состав, сумма, статусы заказа, оплаты и возврата |
| Детали заказа | Доставка, доступная отмена, повторная проверка оплаты |
| Ассистент | Чат, предложения вопросов, источники, переходы к блюдам и своим заказам |
| Кухня и курьер | Минимальные страницы по ролям для существующих операций и показа жизненного цикла |

Общие состояния: загрузка, пустые данные, ошибка сервера, истёкшая сессия, недоступность AI.
Адаптивность, клавиатурная навигация и подписи полей входят в готовность экрана.
Цены, скидки и факт успешной оплаты не определяются клиентом.
Для SSE с Bearer-авторизацией использовать потоковый fetch: штатный EventSource не позволяет задать Authorization.
Схему хранения токенов зафиксировать до реализации входа; предпочтительно refresh в HttpOnly-cookie,
access в памяти, один запрос обновления на конкурентные 401, с учётом CSRF для cookie-операций.
Вход через Google оставить дополнительной задачей: текущий callback возвращает JSON, потребуется браузерный сценарий.

Полноценная корзина с разными блюдами — расширение после основного сценария.
Она требует order_items со снимками названия и цены, миграции старых заказов и адаптации событий и тестов.
В первом варианте интерфейс честно предлагает «Заказать», а не имитирует многопозиционную корзину.

## 5. Платёжный модуль

### Модель и контракты

- `Payment`: заказ, источник/провайдер, сумма, валюта, статус, внешний ID, ключ идемпотентности,
  отпечаток запроса, URL подтверждения, временные метки и последнее состояние ошибки.
- `Refund`: платёж, сумма полного возврата, статус, внешний ID, отдельный ключ идемпотентности.
- Надёжно сохраняемые входящие уведомления и задания проверки неопределённых результатов.
- Состояния оплаты и возврата отделены от состояния выполнения заказа.
- Цена фиксируется при создании заказа. Сервер сверяет сумму, валюту, заказ и объект провайдера.
- Повтор ключа с теми же параметрами возвращает прежний результат; с другими — конфликт.
- Два разных ключа не должны создавать два одновременно действующих платежа за один заказ.

Предварительное API:

- `POST /payments` с order_id и заголовком `Idempotency-Key`.
- `GET /payments/{id}` — только владелец или разрешённая роль.
- `POST /payments/webhook` — входящие уведомления провайдера.
- Детали заказа с составом и состояниями оплаты, возврата и доставки.
- Отмена заказа инициирует возврат через бизнес-сценарий, а не прямой вызов шлюза из браузера.

Адаптер ЮKassa переводит наш `Idempotency-Key` в заголовок провайдера `Idempotence-Key`.
Если для соответствия методичке API принимает amount, это только заявленная сумма:
сервер сравнивает её с собственной суммой и отклоняет расхождение.

### Надёжность и интеграция

1. Сохранить намерение оплаты до запроса провайдеру. Не держать транзакцию БД во время сетевого вызова.
2. При таймауте результат остаётся неопределённым: сверка и повтор с тем же ключом, без нового списания.
3. Повторы с задержками 1, 2, 4, 8 секунд и jitter; бизнес-отказ не повторять как сетевой сбой.
4. После лимита попыток — задача разбора/DLQ и дальнейшая сверка. Таймаут не означает отказ платежа.
5. Подлинность уведомления ЮKassa проверять чтением объекта через авторизованный API.
   Не реализовывать вымышленную HMAC-подпись: отличие от методички описать в ADR.
6. Уведомление сохранять надёжно до подтверждения получения; повторное и запоздавшее событие не откатывает состояние.
7. Подтверждённая оплата и `OrderPaid` попадают в БД/outbox одной транзакцией.
8. Кухня и доставка продолжают получать существующие события. Возврат внешней оплаты не пополняет внутренний баланс.
9. Отмена запускает идемпотентный полный refund; UI показывает ожидание, пока возврат не подтверждён.
10. Обработать гонку отмены и успешной оплаты: поздняя оплата отменённого заказа приводит к возврату,
    а не отправляет его в доставку. Конкурентные операции защищаются состояниями и ограничениями БД.
11. Периодическая сверка восстанавливает результат при пропавшем вебхуке или падении процесса.

Возвращение браузера со страницы шлюза само по себе не подтверждает оплату.
Публичный HTTPS-адрес для вебхуков нужен для настоящего тестового магазина; локально можно использовать туннель.
Для автономных тестов — управляемый fake-адаптер. Его демонстрация не заменяет проверку реального тестового шлюза.

## 6. AI-ассистент

1. Подготовить справку о заказах, оплате и доставке. Для рекомендаций добавить проверенные описания блюд;
   не выводить состав и аллергены из названия блюда.
2. Индексировать справку и меню: текст → эмбеддинги → pgvector → top-k результатов.
3. Хранить источник, ID записи, версию и время обновления; изменения меню должны обновлять индекс.
4. На вопросы по заказам сервер получает только разрешённые пользователю сведения из сервисов.
   Идентификатор пользователя берётся из JWT, а не из сообщения или аргумента модели.
5. Передавать найденные материалы и разрешённые факты в генерацию. Показывать ссылки на источники.
6. Источник цены и текущего статуса — актуальная БД/API; при отсутствии данных ассистент сообщает об этом.
7. Ассистент выполняет операции чтения. Оплата, отмена и возврат доступны через явные действия интерфейса.
8. История чата изолирована по пользователю. Контекст ограничен, запросы имеют таймауты и лимиты.
9. При недоступности модели сайт продолжает работать, чат показывает понятное сообщение.
10. Документы и пользовательский текст считаются недоверенными: они не меняют правила доступа и набор операций.

Предварительное API: `POST /assistant/messages`, чтение своих диалогов и сообщений.
Потоковая генерация — после рабочего RAG и проверки доступа.
Оценка качества: фиксированный набор 25–30 вопросов с ожидаемыми фактами/источниками,
проверки чужих заказов, отсутствующих сведений, провокаций, сбоя модели; медиана/p95 времени ответа.
Логи: идентификаторы запросов, длительности, источники и ошибки; без токенов, секретов и лишних персональных данных.

## 7. Порядок работ и критерии этапов

| Этап | Работа | Критерий завершения |
|---|---|---|
| 0, дни 1–2 | Проверить текущие тесты, уточнить доступ к шлюзу и машине для AI, описать состояния и API | Зафиксированы контракты, ADR и границы объёма |
| 1, дни 3–5 | Compose, proxy, схема денег и источников оплаты, каркас фронтенда, меню и вход | Сайт открывается, пользователь входит и видит реальные блюда |
| 2, дни 6–10 | PaymentGateway, fake и тестовая ЮKassa, вебхуки, outbox, страницы оформления и оплаты | Успешная тестовая оплата даёт один OrderPaid; повтор не списывает дважды |
| 3, дни 11–13 | Возвраты, гонки отмены, сверка, кабинет, страницы кухни и курьера | Отказ доставки запускает один возврат, состояние видно на сайте |
| 4, дни 14–17 | База знаний, эмбеддинги, RAG, контекст заказов и платежей, чат | Ответы опираются на источники; чужие данные недоступны |
| 5, дни 18–20 | Сквозные тесты, нагрузка, метрики, документация и репетиция защиты | Повторяемый показ обоих треков через браузер |

Это оценка для планирования, не обещание календарного срока. Доступы к шлюзу и скорость модели проверяются
в начале, чтобы не оставить внешние зависимости на последнюю неделю.

## 8. Проверки и материалы для оценки 9–10

- Старые тесты и новые тесты переходов состояний, прав доступа и Decimal-расчётов.
- Платежи: конкурентные запросы, разные ключи одного заказа, повтор вебхука, таймаут после обработки шлюзом,
  поздняя оплата после отмены, перезапуск worker, один возврат при дубле события.
- Сквозной браузерный сценарий: вход → меню → оформление → оплата → кабинет → ассистент.
- Нагрузка: 100 одновременных платёжных сценариев на контролируемом адаптере;
  отдельно небольшая проверка настоящего тестового магазина с учётом его ограничений.
- AI: качество на фиксированных вопросах, актуальность индекса, изоляция пользователей, fallback и задержки.
- CI: backend-тесты, миграции, проверка типов и production-сборка фронтенда, ключевые браузерные проверки.
- README с запуском и настройкой, ADR по шлюзу, состояниям оплаты, модели/эмбеддингам и pgvector.
- Отчёт по каждому треку, результаты измерений, ограничения, сценарий защиты и демонстрационные данные.

## 9. Что отложить при нехватке времени

Сначала сокращаются многопозиционная корзина, Google-вход в UI, потоковая генерация, сложная админка
и персональные рекомендации. Сохраняются проверка реального шлюза, компенсации, RAG, защита данных,
работающий интерфейс и материалы для защиты.
Не добавляем отдельные новые микросервисы только ради этих треков: модульные границы уже достаточны.

## 10. Первые конкретные задачи

1. Зафиксировать исходное состояние тестов и модели оплаты.
2. Описать переходы заказа, платежа и возврата, включая гонки.
3. Проверить тестовый магазин ЮKassa, HTTPS-вебхук и кандидата LLM на доступной машине.
4. Подготовить миграции Decimal и источника оплаты и контракты новых API.
5. Собрать Compose и фронтенд с настоящими меню и входом.
6. Довести один заказ до подтверждённой внешней оплаты, затем расширять сценарий.
