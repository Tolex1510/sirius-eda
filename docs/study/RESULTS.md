# Учебная практика: состояние реализации и проверки

Обновлено: 3 ноября 2026. Это отчёт о локальной реализации, не подтверждение окончательной сдачи треков.

## Реализовано

- React/TypeScript: меню, категории и поиск, регистрация и вход, оформление одного блюда с количеством,
  demo-оплата, кабинет, детали заказа, SSE-трекинг, страницы кухни/курьера, чат и справка.
- Браузерная сессия: access в памяти, refresh в HttpOnly-cookie, проверка Origin для cookie-операций.
- Платежи: постоянное намерение, защита от дублей и чужого доступа, Decimal-суммы, отдельный источник оплаты,
  адаптер тестовой ЮKassa, проверка результата через API, OrderPaid в outbox, идемпотентные возвраты.
- Фоновая сверка: Celery, повторы 1/2/4/8 секунд + jitter, DLQ и флаг ручной проверки.
- Согласование отмены с поздней оплатой и действиями доставки. Неоплаченные внешние заказы не создают чеки.
- RAG: pgvector, обновляемый публичный индекс, актуальные цены при retrieval, личный контекст и история
  с проверкой пользователя, адаптер Ollama и явный fallback.
- Полный Compose, миграции, стартовое меню, необязательные аккаунты ролей, профиль Ollama и GPU override.
- Инструкция WSL, ADR, сценарий защиты, 30 вопросов для оценки модели, CI для backend, миграций, сборки и браузера.

Проверены:

- Повторы ключа, конфликт параметров, один OrderPaid при повторных подтверждениях.
- Недоступность чужого платежа, заказа и диалога.
- Сверка суммы, валюты, идентификатора заказа, тестового режима, валюты возврата.
- Запрет подтверждать внешнюю оплату старым `/pay`.
- Возврат после поздней оплаты отменённого заказа и после отказа доставки.
- Запрет поздно назначать доставку уже отменённому заказу и отменять заказ в пути.
- Остановка небезопасного повтора за пределами окна идемпотентности.
- Экспоненциальная задержка задачи сверки и переход к ручной проверке.
- Реальный pgvector: индексация, поиск, отсутствие повторной индексации без изменений,
  актуальная цена до переиндексации и удаление отсутствующих блюд. Использована детерминированная
  тестовая модель, поэтому этот тест проверяет механику хранения/поиска, не качество LLM.
- Новые миграции: установка в пустую PostgreSQL БД, `alembic check`, откат до base,
  повторная установка и повторный `alembic check` без расхождений.

## Доработка строго по этапам трека D

- `amount` обязателен в POST /payments; сервер сверяет его со стоимостью заказа. При расхождении — 409, при отсутствии/некорректном формате — 422.
- `payments_consumer` слушает OrderCancelled через RabbitMQ, сохраняет Inbox и намерение возврата атомарно, затем запускает Celery. Прямая установка refund_status из модуля заказов удалена.
- Поздняя оплата отменённого заказа публикует новое OrderCancelled, чтобы компенсация не потерялась.
- HTTP webhook обрабатывает также refund.succeeded. Успех/отказ/возврат проверяются через API провайдера; дубли не создают повторных эффектов.
- Причина отказа сохраняется, например insufficient_funds. Окончательные HTTP 4xx не повторяются; временные ошибки идут через 1/2/4/8 секунд + jitter и DLQ.
- На настоящем RabbitMQ три копии OrderCancelled дали один вызов возврата.
- [Сага ЮKassa, заказ №108](results/yookassa_saga_refund.json): payment succeeded → delivery.failed → cancelled → payments → refund succeeded. Проверка refund выполнена GET-запросом с тем же сохранённым refund_id.
- [Повтор HTTPS webhook, заказ №106](results/yookassa_duplicate_webhook.json): ответ 503 при временной ошибке проверки, затем два ответа 200; число OrderPaid осталось равным 1. Это ручное воспроизведение webhook с проверкой настоящего объекта ЮKassa.
- [Повтор нагрузки после изменения API](results/payment_probe_methodic.json): 100 одинаковых запросов → 1 платёж, 100 разных заказов → 100 платежей, все ответы 200. Медиана/p95: 4269/5603 мс и 4057/7398 мс; прогон выполнялся на отдельном demo-стенде одновременно с работающим основным стеком, без изоляции фоновой нагрузки.
- Схема после миграции 0011 проверена через alembic check: расхождений нет.

Подробное соответствие и сценарий защиты: [TRACK_D_CHECKLIST.md](TRACK_D_CHECKLIST.md).

HTTPS ingress перенесён в отдельный Docker-сервис `webhook-ssh` с автоматическим переподключением.
