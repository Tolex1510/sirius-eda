# Лабораторная № 10: что и где показывать

## Установка

```bash
.venv/bin/pip install -r requirements.txt -r requirements-lab10.txt
```

Нужен запущенный Docker daemon. Основной Compose поднимать для интеграционных тестов и автоматического нагрузочного эксперимента не требуется. Никакие настоящие платежи и запросы AI не выполняются.

## 1. Пирамида тестов

- Быстрые проверки сервисов и доменных правил — файлы `tests/test_*service.py`, `tests/mutation/`. Без PostgreSQL и сети.
- Проверки HTTP на in-memory репозиториях и fakeredis — обычный набор `tests/`; это компонентные проверки, их нельзя все называть unit-тестами.
- Интеграция HTTP → сервис → SQL-репозиторий → PostgreSQL — `tests/integration/`.
- Контракт сообщения между заказами и кухней — `tests/contracts/`.
- Браузерные E2E — `frontend/e2e/`, команда `npm run test:e2e --prefix frontend`; в CI есть отдельная job `browser`.

## 2. Testcontainers

```bash
.venv/bin/pytest tests/integration -v
```

Показать `tests/integration/conftest.py`: на сессию тестирования создаётся новая `pgvector/pgvector:pg16`, как в проекте. В отдельном процессе выполняется `alembic upgrade head` на URL именно временного контейнера. Не используется копия рабочей БД. После сессии контейнер удаляется.

Перед каждым тестом и после него очищаются все прикладные таблицы через `TRUNCATE … RESTART IDENTITY CASCADE`. Поэтому commit внутри репозитория не оставляет данные следующему тесту. Один rollback в конце фикстуры такой гарантии не дал бы. История Alembic сохраняется. Роли создаются заново.

В FastAPI подменены зависимости репозиториев на **SQL-реализации с временной БД**, а не на in-memory. JWT остаётся настоящим. Подменяются только уведомления и Redis rate limiter, чтобы отдельно проверить SQL и HTTP без внешних сервисов. Lifespan не запускается, чтобы глобальный пул не прогревал БД разработчика.

Показать `tests/integration/test_orders.py`:

1. Создание двух порций: заказ сохранён, сумма 300, баланс изменился с 1000 на 700.
2. Недостаточный баланс: ошибка без заказа и без списания.
3. Недоступное блюдо: ошибка без списания.
4. Повторная отмена: возврат только один раз.
5. Оплата: статус paid и OrderPaid в outbox сохранены.
6. Запрос без JWT: 401 и отсутствие записи.
7. Чистая БД следующего теста.

Реальный API возвращает 200 при создании, поэтому тест ожидает 200; пример с 201 из методички не меняет контракт нашего приложения.

## 3. Locust и узкие места

Сценарий `locustfile_lab10.py`: веса 7:2:1 — меню, карточка, создание заказа. ID берутся из актуального меню, студент определяется по JWT. Введён короткий think time 0,1–0,5 с, чтобы увидеть ограничение при небольшом числе пользователей. Setup-запрос меню учитывается отдельно в статистике. Веса задач — вероятности выбора, а не гарантия точного распределения всех HTTP-запросов.

Автоматический изолированный эксперимент:

```bash
.venv/bin/python scripts/lab10_load.py --seconds 25
```

Скрипт поднимает временные PostgreSQL и Redis, накатывает миграции, создаёт 48 блюд и 200 студентов с тестовым балансом. Токены живут только во временном файле с правами 0600. Далее запускает один процесс настоящего API и четыре ограниченных прогона: sync/50, sync/200, celery/50, celery/200. Для Celery работает отдельный worker на 16 потоков. Между прогонами очищается только очередь временного Redis. Окружение удаляется при завершении или исключении.

Для показа через Grafana в Linux:

```bash
.venv/bin/python scripts/lab10_load.py --seconds 25 --only-200 --monitoring --out docs/lab10/results/monitored
```

Печатается локальный URL отдельной Grafana. Prometheus собирает HTTP-метрики настоящего API и системные показатели эксперимента. Дашборд показывает RPS, p95, CPU процесса API, активные соединения PostgreSQL, очередь Celery и 5xx. В конце сохраняются снимок Grafana и ответы Prometheus; затем временный мониторинг останавливается. Для снимка нужен `npm ci --prefix frontend` и `npx --prefix frontend playwright install chromium`.

Основной вывод: синхронные PDF/email удерживают потоки HTTP примерно на три секунды. Celery снимает эту задержку из HTTP, но не увеличивает мощность фоновых обработчиков автоматически. При 200 пользователях появляется очередь задач и загрузка одного API-процесса около одного ядра. Смотрите [RESULTS.md](RESULTS.md): это измеренный результат короткого эксперимента, не обещание производительности на длительной нагрузке.

Для ручного интерактивного запуска на заранее подготовленном **тестовом** стенде:

```bash
LOCUST_TOKENS=/path/to/private/test-tokens.txt .venv/bin/locust -f locustfile_lab10.py --host=http://127.0.0.1:8000
```

Веб-интерфейс Locust: http://localhost:8089. Сценарий создаёт реальные записи в указанной тестовой БД. Основная страница сайта на 8080 проксирует API под `/api`; при использовании её вместо прямого API укажите host `http://localhost:8080/api`.

## 4. CI и блокировка слияния

`.github/workflows/tests.yml` срабатывает на push и pull_request. Jobs: быстрые тесты с coverage, миграции, сборка фронтенда, браузер, Testcontainers + Pact и mutmut с проверкой улучшения результата. XML тестов, Pact и отчёты мутаций сохраняются в artifacts.

**Состояние:** проект опубликован на GitHub; защита main применена, красный CI и `mergeable_state: blocked` подтверждены. История запусков и исправлений — в [GITHUB.md](GITHUB.md). Наличие YAML само по себе не блокирует кнопку Merge.

Порядок настройки и демонстрации (защита уже применена):

1. Дождаться зелёного workflow.
2. В Settings → Branches → защитить основную ветку, включить Require status checks to pass и выбрать jobs `tests`, `migrations`, `frontend`, `browser`, `integration`, `mutation`. Для ruleset также запретить обход проверки, если он доступен. Пример настроек API — `.github/branch-protection.example.json`; файл сам настройки GitHub не применяет.
3. В отдельной демонстрационной ветке добавить `tests/test_ci_failure_demo.py` с `assert 1 == 2`, открыть PR и показать красную job и недоступное слияние.
4. Удалить демонстрационный тест, дождаться зелёного запуска. Основную ветку специально не ломать.

Локально доказано, что сломанный тест возвращает exit code 1:

```bash
.venv/bin/python scripts/lab10_ci_failure.py
```

Он выполняется во временном каталоге и не оставляет сломанный тест в рабочем наборе. Это не заменяет демонстрацию на GitHub.

## 5. Pact

```bash
PACT_DO_NOT_TRACK=true .venv/bin/pytest tests/contracts -v -s
```

`tests/contracts/test_order_paid.py` независимо описывает ожидания кухни. `Pact.verify` передаёт пример реальному `parse_event` и `KitchenService.accept`. Затем настоящий `OrderService.pay_order` создаёт событие в outbox, и Pact Verifier проверяет его на соответствие контракту.

Негативный тест переименовывает `amount` в `total` только в проверяемом сообщении: Verifier должен обнаружить отсутствующее поле. Его ошибка ожидаема, поэтому сам pytest-тест зелёный. Это не запуск RabbitMQ и не проверка доставки сообщения — транспорт проверяется отдельно.

Контракт использует действующие поля проекта `order_id`, `customer_id`, `amount`, `event_id`, `occurred_at`, `event_type`. В методичке приведён пример `total/currency`; менять уже работающий протокол ради названий из примера не требуется. Валюта сервиса — RUB, отдельного поля currency в OrderPaid сейчас нет.

Сгенерированный контракт: `docs/lab10/pacts/sirius-kitchen-sirius-orders.json`.

## 6. Mutmut

```bash
.venv/bin/python scripts/lab10_mutation.py
.venv/bin/python scripts/lab10_mutation_gate.py
```

Для воспроизводимого сравнения скрипт копирует тот же `app/domain/money.py` во временные каталоги: до — только слабый тест целых рублей, после — плюс проверки округления половинной копейки и некорректных значений. Рабочий код не мутируется. Область намеренно мала: денежное преобразование, 18 мутаций, не всё приложение.

До: 8 убито, 10 выжило. После: 10 убито, 8 выжило. Пойманы изменения аргументов `quantize`, которые тест целых рублей не замечал. Оставшиеся восемь меняют текст ошибки, а тест проверяет тип ValueError; это видно в сохранённых diff. Не заявляется 100% mutation score.

Обычный запуск на итоговом наборе также настроен через `setup.cfg`:

```bash
.venv/bin/mutmut run --max-children 2
.venv/bin/mutmut results
```

Результаты до/после и diff: `docs/lab10/results/mutation-*`. Gate в CI падает, если сравниваются разные количества мутаций, есть непроверенные/ошибочные мутации или добавленные тесты больше не уменьшают число выживших.

## Что отвечать на защите

- **Почему не SQLite?** PostgreSQL проверяет реальные миграции, Numeric, JSONB и pgvector, поведение которых отличается от SQLite.
- **Почему покрытие не равно качеству?** Слабый тест проходит изменённый код: это показал mutmut.
- **Почему не достаточно хорошего RPS?** Нужны p95, ошибки и состояние фоновой очереди: быстрый HTTP может скрывать накопление задач.
- **Зачем Pact?** Ловит несовместимый формат сообщения до выпуска провайдера.
- **Что показывать для окончательной сдачи?** Тесты, нагрузку, красный/зелёный CI и обязательные проверки PR по ссылкам в GITHUB.md. Оба бонуса Pact и mutmut реализованы.
